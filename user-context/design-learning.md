# User Design Learning v0.1

This file contains design judgments that have repeated across prior work. They are evidence about what this user tends to consider better, not fixed rules and not a PatchLog design specification.

Use them only when relevant to the current task. Do not reproduce any previous screen or project-specific visual device.

## Repeated judgments

1. **Visual quality matters alongside clarity.** A result can be correct and usable but still feel weak if composition, spacing, typography, or visual presence are underdeveloped.

2. **Product UI should demonstrate the product.** Prefer showing meaningful product interactions, states, and information over explaining the product with large amounts of descriptive copy.

3. **Avoid generic assembly.** Repeated equal-weight cards, familiar SaaS section patterns, and safe default dashboard composition can make a product feel interchangeable even when technically clean.

4. **Prefer intentional hierarchy.** Important information should clearly dominate secondary information through scale, spacing, density, grouping, and placement rather than giving every element similar visual weight.

5. **Decoration should earn its place.** Visual effects, illustrations, metaphors, or assets are valuable when they strengthen product meaning or comprehension, not when they merely make the surface busier.

6. **One strong product-specific visual idea can be more valuable than many generic effects.** Distinctiveness should come from the product itself rather than from arbitrary styling.

7. **Minimal is not automatically better.** Restraint is useful, but excessive simplification can remove useful density, product character, or visual attraction.

8. **Repetition should add new meaning.** Repeated containers, mockups, or presentation patterns are weak when they only restate the same idea without revealing a new product moment.

## Application boundary

These judgments describe the user's recurring preferences. The model still owns the task-specific art direction and may decide that a particular judgment is less relevant to PatchLog. Preserve PatchLog's functional needs and information density rather than forcing it into a marketing-site aesthetic.
